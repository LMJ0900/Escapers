## 1. 개요

### 1.1 목적

현재 MSW 목(`frontend/src/mocks/handlers/*`)으로 대체 중인 API를 실제 서버로 구현하고, 방탈출 예약 페이지를 **주기적으로 크롤링해 빈자리를 감시**하는 백엔드를 구축한다. 본 문서는 백엔드의 기술 스택, 모노레포 내 구조, 모듈 설계, API 계약, 데이터 모델, 크롤링·작업 큐 파이프라인, 운영 요구사항을 정의한다. 빈자리 알림 발송은 차기 개발 사항으로 미루고 [§8](#8-차기-개발-사항--알림)에 설계만 남긴다.

### 1.2 범위

- **포함**: 인증(JWT), 회원, 테마·지점 조회/필터, 좋아요, 예약 내역, 크롤러(테마 정보 수집 · 예약 빈자리 감시), 작업 큐. 1차에서 감시 결과는 서비스 화면(감시 목록)에서 확인한다.
- **불포함(차기)**: 빈자리 알림 발송(웹 푸시 · 이메일 · 카카오 알림톡 — [§8](#8-차기-개발-사항--알림)), 예약 대행/결제, 리뷰·게시판·댓글 API(요구사항 명세서 M2 범위 — 별도 문서), 관리자 대시보드 UI.

### 1.3 용어 정의

| 용어             | 정의                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------- |
| 소스(Source)     | 크롤링 대상 예약 사이트. 브랜드 단위로 하나 이상 존재하며 파서(어댑터)를 가진다           |
| 어댑터(Adapter)  | 소스별 크롤링 구현체. 정적 HTML이면 Cheerio, JS 렌더링 페이지면 Playwright를 사용한다     |
| 슬롯(Slot)       | 특정 테마의 특정 일시 예약 단위. 상태: 예약 가능 / 마감                                   |
| 감시(Watch)      | 회원이 "이 테마의 이 날짜(시간대)에 빈자리가 있는지 지켜봐줘"라고 등록한 조건             |
| 스냅샷(Snapshot) | 한 번의 크롤링으로 얻은 슬롯 목록. 직전 스냅샷과 비교(diff)해 "마감 → 가능" 변화를 찾는다 |
| 작업(Job)        | BullMQ 큐에 들어가는 비동기 작업 단위(크롤링, 비교, 정리 등)                              |

### 1.4 기술 스택

| 영역             | 선택                                                 | 비고                                                                    |
| ---------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| 언어 / 런타임    | TypeScript · Node.js (LTS)                           | 프론트와 언어 통일, `shared` 패키지로 타입·스키마 공유                  |
| API 서버         | **NestJS** (어댑터: Fastify)                         | 모듈/DI 구조. 가볍게 가야 할 경우 순수 Fastify로 대체 가능(§10 미결 1)  |
| 크롤링           | **Playwright** (JS 렌더링) + **Cheerio** (정적 HTML) | 소스별 어댑터로 선택                                                    |
| 작업 큐 / 스케줄 | **BullMQ** + **Redis**                               | 반복 작업(repeatable job), 재시도·백오프, 동시 실행 수 제한, rate limit |
| DB               | **PostgreSQL** + **Prisma**                          | Drizzle 대안(§10 미결 2)                                                |
| 검증             | **zod** (`shared` 스키마 재사용)                     | 프론트 `frontend/src/api/**/request/*.ts`의 zod 스키마와 동일 규칙               |

## 2. 시스템 구성

### 2.1 모노레포 구조

```
Escapers/
├─ frontend/          ← Next.js (App Router)
├─ backend/           ← 본 문서 대상 (NestJS)
├─ shared/            ← 프론트·백엔드 공용 zod 스키마 · DTO 타입 · 에러 코드
├─ docs/
├─ package.json       ← npm workspaces: ["frontend", "backend", "shared"]
└─ tsconfig.base.json
```

### 2.2 프로세스 구성

API 서버와 워커는 **같은 코드베이스, 다른 엔트리포인트**로 실행한다. 크롤링(특히 Playwright)은 CPU·메모리를 많이 쓰므로 API 응답 지연에 영향을 주지 않게 프로세스를 분리한다.

```
                ┌──────────────────────┐
  브라우저 ───▶ │ frontend (Next.js)   │
                │  - RSC / proxy.ts    │──── REST (Authorization: Bearer) ───┐
                └──────────────────────┘                                     ▼
                                                              ┌─────────────────────────┐
                                                              │ backend: api (main.ts)  │
                                                              │  NestJS HTTP            │
                                                              └──────┬───────────┬──────┘
                                                                     │ Prisma    │ enqueue
                                                                     ▼           ▼
                                                              ┌───────────┐ ┌───────────┐
                                                              │PostgreSQL │ │  Redis    │
                                                              └───────────┘ └─────┬─────┘
                                                                     ▲            │ consume
                                                                     │            ▼
                                                              ┌─────────────────────────┐
                                                              │ backend: worker         │
                                                              │  (worker.ts)            │
                                                              │  - crawl 큐 (Playwright/Cheerio)
                                                              │  - diff  큐             │
                                                              └─────────────────────────┘
```

| 프로세스    | 엔트리포인트      | 역할                                                               | 수평 확장                               |
| ----------- | ----------------- | ------------------------------------------------------------------ | --------------------------------------- |
| `api`       | `src/main.ts`     | REST API, 감시 등록 시 작업 등록                                   | 무상태 → 인스턴스 증설                  |
| `worker`    | `src/worker.ts`   | BullMQ 프로세서(크롤링 · diff · 정리)                              | 큐별 `concurrency` 조절 / 인스턴스 증설 |
| `scheduler` | (`worker`에 포함) | 반복 작업(repeatable job) 등록 · 정리. 중복 등록 방지를 위해 1개만 | 단일                                    |

## 3. API 공통 규약

### 3.1 기본

- Base URL: `NEXT_PUBLIC_API_BASE_URL` (프론트 `.env.development`). 경로 접두사는 없다(프론트 목 핸들러가 `*/auth/login`, `*/theme` 형태로 매칭).
- 요청·응답 본문은 JSON, 문자 인코딩 UTF-8, 일시는 **ISO 8601 + 오프셋**(예: `2026-10-03T18:00:00+09:00`).
- ID는 문자열로 내려준다(프론트 타입이 `id: string`). DB는 `cuid`/`uuid` 사용.
- 열거형 값은 **대문자 스네이크**(`HORROR`, `CONFIRMED`). 단, 기존 계약인 `ThemeCollectionType`(`hot`/`horror`/`active`)은 소문자를 유지한다.

### 3.2 응답 엔벨로프

[공통 에러 명세서 §1](./에러명세서/공통%20에러%20명세서.md)을 그대로 따른다. 모든 컨트롤러 반환값은 전역 인터셉터가 감싸고, 모든 예외는 전역 필터가 변환한다.

```jsonc
// 성공
{ "result": "SUCCESS", "data": { /* ... */ }, "error": null }

// 실패 — HTTP status 와 error.status 를 일치시킨다
{ "result": "ERROR", "data": null,
  "error": { "code": "AUTH_INVALID_CREDENTIALS", "message": "이메일 또는 비밀번호가 올바르지 않습니다.", "status": 401 } }
```

| 상황                    | HTTP | `error.code`                                                       |
| ----------------------- | ---- | ------------------------------------------------------------------ |
| 요청 검증 실패(zod)     | 400  | `VALIDATION_FAILED`                                                |
| 토큰 없음 / 위조 / 만료 | 401  | `AUTH_TOKEN_MISSING` / `AUTH_TOKEN_INVALID` / `AUTH_TOKEN_EXPIRED` |
| 정지·탈퇴 계정          | 403  | `AUTH_ACCOUNT_SUSPENDED` / `AUTH_ACCOUNT_WITHDRAWN`                |
| 리소스 없음             | 404  | `<DOMAIN>_NOT_FOUND`                                               |
| 중복 등 비즈니스 충돌   | 409  | 도메인별 (`AUTH_EMAIL_DUPLICATE` 등)                               |
| Rate limit 초과         | 429  | `RATE_LIMITED`                                                     |
| 처리되지 않은 예외      | 500  | `INTERNAL_ERROR` (내부 메시지 노출 금지)                           |

- 에러 코드는 `shared/src/errors/`에 상수로 정의해 프론트(`frontend/src/api/domain/*/*.error.ts`)와 백엔드가 같은 값을 import한다.
  - **현재 구현**: `shared`는 아직 비어 있다. 백엔드는 공통 코드를 `backend/src/common/exception/error-code.ts`(`COMMON_ERROR`)에, 도메인 코드를 각 모듈의 `*.error.ts`(`AUTH_ERROR`, `USER_ERROR`, `THEME_ERROR`)에 두고, 프론트와 같은 문자열 값을 쓴다. 공통 코드 중 구현된 것은 `VALIDATION_FAILED` · `NOT_FOUND` · `INTERNAL_ERROR`이며, `RATE_LIMITED`는 rate limit 도입 시 추가한다.
- 새 `code`를 추가하면 해당 도메인 에러 명세서에 함께 등록한다.

### 3.3 인증

- 로그인/재발급 응답 본문으로 `accessJwt`, `refreshJwt`를 내려주고, **쿠키 설정은 프론트(Next 서버)가 담당**한다(현재 `frontend/src/proxy.ts`, `frontend/src/constant/token` 구조 유지).
- 보호된 API는 `Authorization: Bearer <accessJwt>` 헤더로 인증한다.
- accessToken: 짧은 수명(예: 15분), refreshToken: 긴 수명(예: 14일). refreshToken은 **DB에 해시로 저장**하고 재발급 시 회전(rotation)한다. 이미 사용된 refreshToken이 다시 오면 해당 계열 전체를 폐기한다(탈취 감지).
- 공개 API 중 **로그인 시 개인화 정보가 붙는 것**(예: 테마 목록의 `liked`)은 "선택 인증"으로 처리한다. 토큰이 없으면 비로그인으로 응답하고, 토큰이 있는데 유효하지 않으면 401을 반환한다.

### 3.4 페이지네이션

- 목록은 **커서 기반**을 기본으로 한다: 요청 `cursor`, `size`(기본 20, 최대 50) / 응답 `items`, `nextCursor`(`null`이면 마지막), `totalCount`.
- 커서는 정렬 키 + id를 base64url로 인코딩한 **불투명 문자열**이다. 클라이언트는 해석하지 않는다(현재 목의 "인덱스 문자열" 방식은 대체한다).

### 3.5 보안 · 공통 정책

- CORS: 프론트 오리진만 허용. 쿠키를 쓰지 않으므로 `credentials: false`(프론트 `withCredentials: false`와 일치).
- Rate limit: 인증 엔드포인트 IP당 분당 10회, 쓰기 API 사용자당 분당 60회(Redis 카운터).
- 비밀번호는 argon2id로 해시. 로그인 실패 메시지로 계정 존재 여부를 노출하지 않는다.
- 요청 로그에서 `password`, `*Jwt`, `Authorization` 값은 마스킹한다.

## 4. API 명세

> 각 엔드포인트의 요청/응답 타입은 현재 프론트 코드(`frontend/src/api/domain/**`)가 계약이다. 백엔드 구현 시 이 타입을 `shared`로 옮기고 양쪽에서 import한다.

### 4.1 인증 (AUTH)

| 메서드 | 경로            | 인증 | 요청                                                                        | 응답 `data`                 | 주요 에러 코드                                                                 |
| ------ | --------------- | ---- | --------------------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------ |
| POST   | `/auth/signup`  | ✗    | `email, password, nickname, termsAgree, privacyAgree, marketingAgree, role` | `{ email }`                 | `AUTH_EMAIL_DUPLICATE`, `AUTH_NICKNAME_DUPLICATE`                              |
| POST   | `/auth/login`   | ✗    | `email, password`                                                           | `{ accessJwt, refreshJwt }` | `AUTH_INVALID_CREDENTIALS`, `AUTH_ACCOUNT_SUSPENDED`, `AUTH_ACCOUNT_WITHDRAWN` |
| POST   | `/auth/reissue` | ✗    | `refreshJwt`                                                                | `{ accessJwt }`             | `AUTH_TOKEN_INVALID`, `AUTH_TOKEN_EXPIRED`                                     |
| POST   | `/auth/logout`  | ✗    | `refreshJwt`                                                                | `null`                      | — (이미 무효인 토큰도 성공 처리, 멱등)                                         |

- `signup`의 `role`은 클라이언트가 보내더라도 **서버는 `MEMBER`만 허용**한다. `ADMIN`/`OWNER`는 관리자 기능으로만 부여한다.
- `termsAgree`·`privacyAgree`가 `false`면 400 `VALIDATION_FAILED`. 동의 시각은 `UserConsent`에 기록한다.

### 4.2 회원 (USER)

| 메서드 | 경로                    | 인증 | 요청                               | 응답 `data`                                     | 주요 에러 코드                   |
| ------ | ----------------------- | ---- | ---------------------------------- | ----------------------------------------------- | -------------------------------- |
| GET    | `/user/getMe`           | ✓    | —                                  | `{ id, role, email, nickname, marketingAgree }` | 공통 인증 에러                   |
| PATCH  | `/user/nickname`        | ✓    | `{ nickname }`                     | `getMe` 응답과 동일                             | `USER_NICKNAME_DUPLICATE`        |
| PATCH  | `/user/email`           | ✓    | `{ email }`                        | `{ email }`                                     | `USER_EMAIL_DUPLICATE`           |
| PATCH  | `/user/password`        | ✓    | `{ currentPassword, newPassword }` | `null`                                          | `USER_CURRENT_PASSWORD_MISMATCH` |
| PATCH  | `/user/marketing-agree` | ✓    | `{ marketingAgree }`               | `getMe` 응답과 동일                             | —                                |
| DELETE | `/user/me`              | ✓    | —                                  | `null`                                          | —                                |

- 비밀번호 변경 성공 시 해당 사용자의 refreshToken을 모두 폐기한다(다른 기기 로그아웃).
- 마케팅 동의는 값이 실제로 바뀔 때만 `UserConsent(type = MARKETING)` 이력을 남긴다.
- 탈퇴: `status = WITHDRAWN`, 개인정보(이메일·닉네임) 익명화(`withdrawn-<id>` — 원래 이메일·닉네임으로 재가입 가능), 감시(Watch) 삭제, refreshToken 폐기. Watch 삭제는 Watch 모델이 추가되면 같은 트랜잭션에 넣는다.
- `getMe`에서 토큰의 사용자가 없으면 현재 공통 코드 `NOT_FOUND`(404)를 반환한다([User 에러명세서 §3.1](./에러명세서/User%20에러명세서.md#31-getme-get-usergetme)의 `USER_NOT_FOUND`와 다름 — 정리 필요).
- 닉네임 변경 주기 제한은 미결(요구사항 명세서 §11-8). 확정 전까지 제한 없이 구현한다.

### 4.3 테마 (THEME)

| 메서드 | 경로                       | 인증 | 요청                                                                                  | 응답 `data`                                                  | 주요 에러 코드               |
| ------ | -------------------------- | ---- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------- |
| GET    | `/theme`                   | 선택 | query: `brands, regions, genres, activityLevels`(쉼표 구분), `sort`, `cursor`, `size` | `{ items: ThemeListItem[], nextCursor, totalCount, facets }` | `VALIDATION_FAILED`          |
| GET    | `/theme/collections/:type` | 선택 | `type`: `hot` \| `horror` \| `active`                                                 | `ThemeListItem[]`                                            | `THEME_COLLECTION_NOT_FOUND` |
| PUT    | `/theme/:id/like`          | ✓    | `{ liked: boolean }`                                                                  | `{ liked }`                                                  | `THEME_NOT_FOUND`            |

- `ThemeListItem`: `id, rank?, name, brandName, branchName, region, genre, difficulty, priceFrom, activityLevel, imageUrl, liked`.
  - `difficulty` · `priceFrom` · `activityLevel` · `imageUrl`은 크롤링 소스에 정보가 없으면 `null`이다. 프론트는 `null`이면 해당 표시를 숨긴다.
  - `imageUrl`은 크롤링한 **원본 포스터 URL**이다. 프론트는 Next 이미지 최적화(`next/image`)로 프록시·리사이즈·캐시(`minimumCacheTTL` 1일)한다. 허용 호스트는 `frontend/next.config.ts`의 `images.remotePatterns`에 있으므로, **크롤링 소스를 추가하면 그 이미지 호스트도 함께 추가**한다(목록 밖 URL은 400).
- `genre`: `HORROR` · `THRILLER` · `MYSTERY` · `SF` · `FANTASY` · `ADVENTURE` · `DRAMA` · `ROMANCE` · `COMEDY` · `IMMERSIVE` · `OUTDOOR` · `ETC` (크롤러 정규화 장르. 원문은 `Theme.genreRaw`).
- `sort`: `POPULAR`(기본) · `NEWEST` · `PRICE_ASC` · `PRICE_DESC` · `DIFFICULTY_DESC` · `DIFFICULTY_ASC`. 허용되지 않는 값은 400.
- `facets`는 **현재 필터를 적용하기 전 전체 기준** 옵션별 개수다(목 동작과 동일). 집계 비용이 크면 Redis에 5분 캐시한다.
- `POPULAR`은 최근 30일 좋아요 수 + 감시 등록 수의 가중합(`Theme.popularityScore`)으로 정렬하고, 배치 작업이 1시간마다 갱신한다.
- 좋아요는 `PUT` + 목표 상태(`liked`) 방식으로 **멱등**하다. 연타해도 최종 상태만 반영된다.
- 컬렉션 정의: `hot` = 인기 점수 상위 N, `horror` = 장르 `HORROR` 인기순, `active` = `activityLevel = HIGH` 인기순. `rank`는 `hot`에서만 채운다.

### 4.4 예약 내역 (RESERVATION)

| 메서드 | 경로              | 인증 | 요청 | 응답 `data`                                                                              |
| ------ | ----------------- | ---- | ---- | ---------------------------------------------------------------------------------------- |
| GET    | `/reservation/me` | ✓    | —    | `Reservation[]` — `id, themeName, branchName, scheduledAt, headcount, status, hasReview` |

- 예약 대행은 범위 밖이므로, 1차에서는 회원이 **직접 기록**한 예약을 **수동 등록**하는 방식으로 한다(§10 미결 4). 등록 API(`POST /reservation`)는 해당 미결 사항이 확정되면 추가한다.

### 4.5 빈자리 감시 (WATCH) — 신규

| 메서드 | 경로         | 인증 | 요청                                                | 응답 `data` | 주요 에러 코드                                                                           |
| ------ | ------------ | ---- | --------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------- |
| GET    | `/watch/me`  | ✓    | —                                                   | `Watch[]`   | —                                                                                        |
| POST   | `/watch`     | ✓    | `{ themeId, date, timeFrom?, timeTo?, headcount? }` | `Watch`     | `THEME_NOT_FOUND`, `WATCH_DUPLICATE`, `WATCH_LIMIT_EXCEEDED`, `WATCH_SOURCE_UNSUPPORTED` |
| DELETE | `/watch/:id` | ✓    | —                                                   | `null`      | `WATCH_NOT_FOUND`                                                                        |

- `Watch`: `id, themeId, themeName, branchName, date, timeFrom, timeTo, status, availableSlots, lastCheckedAt, createdAt`.
- `status`: `ACTIVE`(감시 중, 빈자리 없음) · `AVAILABLE`(조건에 맞는 빈자리 있음) · `EXPIRED`(감시 날짜 경과) · `CANCELLED`.
- `availableSlots`: 현재 예약 가능한 슬롯의 `startsAt` 목록과 예약 페이지 링크. `lastCheckedAt`: 마지막으로 크롤링에 성공한 시각. 실시간이 아니므로 화면에 "마지막 확인: N분 전"으로 표시한다.
- 1차에서는 회원이 감시 목록 화면에서 상태를 확인한다. 알림 채널 선택(`channels`)은 [§8](#8-차기-개발-사항--알림)에서 추가한다.
- 회원당 활성 감시 최대 10개(`WATCH_LIMIT_EXCEEDED`). 같은 테마·날짜·시간대 중복 등록 불가(`WATCH_DUPLICATE`).
- 크롤링 어댑터가 없는 소스의 테마는 등록할 수 없다(`WATCH_SOURCE_UNSUPPORTED`).

## 6. 크롤링

### 6.1 어댑터 인터페이스

```ts
// backend/src/modules/crawler/adapters/crawler.adapter.ts
export interface CrawlerAdapterContext {
  baseUrl: string; // Source.baseUrl
  fetcher: PoliteFetcher; // §6.3 정책을 강제하는 HTTP 클라이언트. 어댑터는 fetch 를 직접 쓰지 않는다
}

export interface CrawlerAdapter {
  readonly key: string; // Source.adapterKey 와 매칭
  readonly engine: "CHEERIO" | "PLAYWRIGHT";
  /** 소스 최초 등록 시 쓰는 기본값 (Brand.name · Source.baseUrl) */
  readonly defaults: { brandName: string; baseUrl: string };

  /** 테마 메타데이터 수집 (최초 1회 · 변경 감지 시 · 주 1회 보정 — §7.3) */
  fetchThemes(ctx: CrawlerAdapterContext): Promise<CrawledThemesResult>;

  /** (예정) 특정 날짜 범위의 슬롯 상태 수집 (주기 감시, §7.2 구현 시 추가) */
  fetchSlots?(
    ctx: CrawlerAdapterContext,
    themes: Theme[],
    dates: string[]
  ): Promise<CrawledSlotsResult>;
}

interface CrawledThemesResult {
  branches: CrawledBranch[]; // externalId, name, address, lat?, lng?, phone?
  themes: CrawledTheme[]; // externalId, branchExternalId, name, *Raw 문자열, description?, imageUrl?, detailUrl
}

interface CrawledSlotsResult {
  slots: CrawledSlot[];
  /** 예약 페이지에서 확인된 테마의 externalId 목록. 테마 변경 감지(§7.3)에 쓴다 */
  seenExternalIds: string[];
}
```

- 어댑터는 사이트 값을 **원문 문자열 그대로**(`genreRaw`, `difficultyRaw`, `playersRaw`, `playTimeRaw`, `priceRaw`) 넘기고, enum 매핑·숫자 변환은 `normalize/theme.normalizer.ts`가 맡는다.
- 사이트별 구현은 `adapters/<brand>.adapter.ts`로 하나씩 두고, `adapter.registry.ts`의 `ADAPTERS` 배열에 등록해 `adapterKey`로 찾는다.
- **엔진 선택 기준**: 응답 HTML 안에 슬롯 데이터가 있거나 내부 JSON API를 호출할 수 있으면 → `fetch` + Cheerio(가볍고 빠름). JS가 렌더링해야 데이터가 보이면 → Playwright.
- Playwright를 쓸 때도 가능하면 **페이지가 호출하는 내부 XHR 응답을 가로채서**(`page.waitForResponse`) JSON으로 파싱한다. DOM 셀렉터보다 사이트 변경에 덜 깨진다.
- 파서 출력은 zod 스키마로 검증한다. 검증 실패는 "사이트 구조 변경" 신호이므로 `CRAWL_PARSE_FAILED`로 분류하고 운영자에게 알린다.

### 6.2 Playwright 운영

- 워커 프로세스당 **브라우저 1개**, 작업마다 새 `BrowserContext`를 연다(쿠키·세션 격리). 작업이 끝나면 context를 반드시 닫는다.
- 이미지·폰트·미디어 요청은 `page.route`로 차단해 속도와 트래픽을 줄인다.
- 페이지 타임아웃 30초, 작업 전체 타임아웃 60초. 브라우저는 N개 작업마다 또는 메모리 임계치 초과 시 재시작한다.
- 컨테이너 배포 시 Playwright 공식 이미지를 사용한다(`mcr.microsoft.com/playwright`). 이미지에 포함된 브라우저 버전과 npm 패키지 버전을 맞춘다.

### 6.3 크롤링 정책 (필수 준수)

- 대상 사이트의 **이용약관과 `robots.txt`를 확인**하고, 크롤링이 금지된 소스는 등록하지 않는다(`Source.enabled = false`).
- 소스(도메인)별 요청 간격 하한을 둔다. 기본 1소스 동시 1요청, 최소 간격 3초. BullMQ의 큐별 `limiter`와 그룹별 동시성으로 강제한다.
- 실제 감시 중인 `Watch`가 있는 테마·날짜만 슬롯을 조회한다(**수요 기반 크롤링**). 감시가 없는 날짜는 조회하지 않는다.
- User-Agent에 서비스 식별자와 연락처를 넣는다. 로그인·CAPTCHA·봇 차단을 우회하지 않는다. 차단 응답(403/429, CAPTCHA 페이지)을 감지하면 해당 소스를 자동으로 일시 중지하고 운영자에게 알린다.
- 수집한 데이터는 서비스 내 표시에만 쓰고, 원문 페이지를 그대로 재배포하지 않는다.
- **구현**: `http/polite-fetcher.ts`(`PoliteFetcher`)가 위 정책을 강제한다.
  - 요청 전 오리진의 `robots.txt`(`User-agent: *` 그룹, 가장 긴 접두사 규칙 우선)를 확인하고, 금지 경로면 `CrawlDisallowedError`로 요청하지 않는다.
  - 오리진별로 요청을 직렬화하고 요청 사이에 `CRAWLER_MIN_INTERVAL_MS`(기본 3초)를 둔다. 요청 타임아웃 30초.
  - 403/429 응답은 `CrawlBlockedError` → 해당 `Source.enabled = false`로 자동 중지한다.
  - `getHtml(url)`(GET)과 `postForm(url, form, { referer })`(폼 POST)를 제공한다. POST는 화면 조각을 POST로만 내려주는 사이트(예: 예약 화면 AJAX)의 **조회 요청에만** 쓰고, 예약 생성처럼 상태를 바꾸는 요청에는 쓰지 않는다.

### 6.5 테마 수집 · 저장 규칙 (`theme-crawl.service.ts`)

1. `ensureSource(adapterKey)`: `Source`가 없으면 어댑터 `defaults`로 `Brand` · `Source`를 만든다(소스 최초 등록).
2. `CrawlRun(kind = themes, reason)`을 `RUNNING`으로 만들고 어댑터 `fetchThemes`를 호출한다.
3. 지점·테마를 zod 스키마로 검증한다. **유효 테마가 0개이거나 검증 실패 비율이 30% 초과**면 사이트 구조 변경으로 보고(`CrawlParseError`) 아무것도 저장하지 않는다.
4. 같은 `externalId` 테마가 여러 번 오면(여러 지점 목록에 실린 경우) 첫 번째만 저장한다.
5. 한 트랜잭션에서 지점을 upsert하고, 기존 테마를 한 번에 읽어 비교한다.
   - 신규 → create (`created`)
   - 필드 값이 바뀜 → update + `lastSeenAt` 갱신 (`updated`)
   - 바뀐 필드 없음 → `lastSeenAt`만 갱신해 `updatedAt`이 "실제 변경 시각"으로 남게 한다 (`unchanged`)
   - `CLOSED`였던 테마가 다시 나타나면 `OPEN`으로 되돌린다.
6. 검증 실패가 **0건일 때만** 결과에 없는 `OPEN` 테마를 `CLOSED`로 바꾼다(`closed`). 일부라도 실패했으면 "안 보인 테마"를 판단할 수 없으므로 종료 처리하지 않는다.
7. 결과: 실패 0건이면 `SUCCESS`, 일부 실패면 `PARTIAL`. `Source.lastSuccessAt` 갱신, `consecutiveFailures = 0`. 예외 시 `FAILED` + `consecutiveFailures` 증가(차단이면 소스 비활성화).

| 큐 이름        | 생산자                                   | 작업 데이터                     | 동시성 / 제한                       | 재시도                      |
| -------------- | ---------------------------------------- | ------------------------------- | ----------------------------------- | --------------------------- |
| `crawl:themes` | 소스 등록 시 · `slots:diff`(변경 감지) · 스케줄러(주 1회) · 관리자 수동 실행 — [§7.3](#73-테마-정보-수집--갱신) | `{ sourceId, reason }` | 2 | 3회, 지수 백오프(1분 시작)  |
| `crawl:slots`  | 스케줄러 (`Source.crawlIntervalSec`마다) | `{ sourceId, themeIds, dates }` | 워커당 4(Playwright 기준), 소스당 1 | 2회, 지수 백오프(30초 시작) |
| `slots:diff`   | `crawl:slots` 완료 시                    | `{ crawlRunId }`                | 8                                   | 3회                         |
| `maintenance`  | 스케줄러                                 | `{ task }`                      | 1                                   | 1회                         |

- `maintenance` 작업: 인기 점수 갱신(1시간), 지난 감시 `EXPIRED` 처리 · 예약 `COMPLETED` 처리(1시간), `CrawlRun` 30일 이전 데이터 삭제(매일).

### 7.2 빈자리 감지 흐름

```
[scheduler] ─▶ crawl:slots(sourceId, 감시 중인 theme·date 목록)
                 │  어댑터.fetchSlots → Slot upsert, CrawlRun 기록
                 ▼
             slots:diff(crawlRunId)
                 │  available 이 바뀐 Slot 찾기 → SlotChange 기록
                 │  조건에 맞는 Watch 조회 (theme, date, 시간대)
                 │  seenExternalIds ↔ DB 테마 비교 → 차이 있으면 crawl:themes 등록 (§7.3)
                 ▼
             Watch 갱신
                 │  조건에 맞는 빈자리 있음 → status = AVAILABLE
                 │  빈자리 없어짐          → status = ACTIVE
                 └  lastCheckedAt = CrawlRun 완료 시각
```

- 크롤링이 실패했거나 일부만 수집된 경우(`CrawlRun.status`가 `FAILED`/`PARTIAL`) 누락된 슬롯을 "마감"으로 보지 않는다. 해당 Watch의 상태를 바꾸지 않고 `lastCheckedAt`도 갱신하지 않는다.
- 알림 발송은 [§8.4](#84-작업-큐--흐름-추가)에서 이 흐름 끝에 `notify` 큐를 붙이는 방식으로 추가한다.
- 반복 작업은 BullMQ `upsertJobScheduler`(job scheduler)로 등록하고, `Source` 설정이 바뀌면 같은 키로 갱신한다.
- 실패한 작업은 `removeOnFail` 대신 일정 기간 보관해 대시보드(Bull Board 등, 관리자 전용)에서 확인한다.

### 7.3 테마 정보 수집 · 갱신

테마 정보는 매일 다시 가져오지 않는다. **최초 1회 수집해 저장하고, 이후에는 빈자리 감시(`crawl:slots`)를 주기적으로 돌리며 테마는 변경이 감지됐을 때만 다시 수집**한다.

> **현재 구현**: BullMQ 큐는 아직 없다. 테마 수집은 CLI(`backend/src/crawl.ts`)로 수동 실행하며, 저장 규칙은 [§6.5](#65-테마-수집--저장-규칙-theme-crawlservicets)를 따른다.
>
> ```
> npm run crawl -w @escapers/backend -- <nextedition | zeroworld | jigubyeol | all> [INITIAL|MANUAL]
> ```
>
> 사유를 생략하면 `Source.lastSuccessAt`이 없을 때 `INITIAL`, 있으면 `MANUAL`로 기록한다. `CHANGE_DETECTED` · `WEEKLY`는 큐 도입 후 사용한다.

| 수집                  | 시점                                                 | 비고                                                    |
| --------------------- | ---------------------------------------------------- | ------------------------------------------------------- |
| 테마 최초 수집        | 소스 등록 시 1회 (관리자가 수동 실행)                | `crawl:themes`, `reason: INITIAL`                       |
| 빈자리 감시           | `Source.crawlIntervalSec` 주기, 감시 중인 테마·날짜만 | `crawl:slots` ([§7.2](#72-빈자리-감지-흐름))            |
| 테마 재수집 — 이벤트  | 슬롯 크롤링 중 테마 변경이 감지될 때                  | `reason: CHANGE_DETECTED`                               |
| 테마 재수집 — 정기    | 주 1회                                               | 이벤트로 못 잡는 가격 · 인원 변경 보정. `reason: WEEKLY` |
| 테마 재수집 — 수동    | 관리자가 "지금 갱신" 실행 (정보 오류 제보 등)         | `reason: MANUAL`                                        |

- **변경 감지 기준** (`slots:diff`에서 `seenExternalIds`와 해당 소스의 `OPEN` 테마를 비교):
  - 예약 페이지에 DB에 없는 테마가 보인다 → 신규 테마 의심
  - DB의 `OPEN` 테마가 예약 페이지에서 보이지 않는다 → 종료 의심
  - `crawl:slots`가 `SUCCESS`일 때만 비교한다. `FAILED`/`PARTIAL`이면 변경으로 보지 않는다.
- **중복 방지**: `crawl:themes` 작업 ID를 `themes:{sourceId}`로 고정해, 같은 소스의 재수집이 대기 중이면 새로 쌓지 않는다.
- **종료 처리**: `crawl:themes`가 `SUCCESS`로 끝났는데 결과에 없는 `OPEN` 테마는 `status = CLOSED`로 바꾼다(삭제하지 않는다 — 좋아요 · 예약 내역 · 리뷰가 참조). 다시 나타나면 `OPEN`으로 되돌린다. `CLOSED` 테마에 걸린 `ACTIVE` 감시는 `EXPIRED` 처리한다.
- 정기 재수집은 소스별로 시각을 분산해 `upsertJobScheduler`로 등록한다(모든 소스가 같은 시각에 몰리지 않게).

## 8. 차기 개발 사항 — 알림

> 1차 범위에서 제외한다. 아래는 이후 개발 시 참고할 설계 초안이며, 1차 구현에서는 이 장의 모듈·테이블·환경변수를 만들지 않는다.

### 8.1 알림 채널

| 채널          | 구현                                 | 필요 정보 / 동의                         | 비고                                                                                     |
| ------------- | ------------------------------------ | ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| 웹 푸시       | `web-push` (VAPID)                   | 브라우저 구독 (`PushSubscription`)       | 응답이 404/410이면 구독을 삭제한다. 프론트에 Service Worker 필요(MSW 워커와 별도 파일).  |
| 이메일        | SMTP 또는 SES 등 (§8.6 미결 2)       | 인증된 이메일                            | 수신 거부 링크 포함. 감시 알림은 거래성 메시지로 분류한다.                               |
| 카카오 알림톡 | 알림톡 발송 대행사 API (§8.6 미결 1) | 전화번호 + 수신 동의, 사전 승인된 템플릿 | 템플릿은 카카오 검수를 거쳐야 하므로 `templateKey`↔템플릿 코드 매핑을 설정으로 관리한다. |

- 채널 구현은 `NotificationChannel` 인터페이스(`send(user, templateKey, payload)`) 하나로 통일하고, `backend/src/modules/notification/`(`channels/`, `templates/`, `notify.processor.ts`)에 둔다.
- 알림 본문에는 테마명·지점명·일시·예약 페이지 링크를 넣는다. **예약 링크는 `Source.baseUrl` 기준 공식 페이지로만 생성**한다.

### 8.2 API 추가

| 메서드 | 경로                              | 인증 | 요청                                       | 응답 `data`                         |
| ------ | --------------------------------- | ---- | ------------------------------------------ | ----------------------------------- |
| GET    | `/notification/vapid-public-key`  | ✗    | —                                          | `{ publicKey }`                     |
| POST   | `/notification/push-subscription` | ✓    | `PushSubscription` JSON (`endpoint, keys`) | `null`                              |
| DELETE | `/notification/push-subscription` | ✓    | `{ endpoint }`                             | `null`                              |
| GET    | `/notification/me`                | ✓    | query: `cursor, size`                      | `{ items, nextCursor }` — 발송 이력 |

- `POST /watch` 요청에 `channels`(`WEB_PUSH` · `EMAIL` · `ALIMTALK` 중 1개 이상)를 추가한다. 선택한 채널의 수신 수단(푸시 구독, 이메일 인증, 전화번호 동의)이 없으면 400.
- 알림톡용 전화번호 등록·인증 API는 §8.6 미결 1 확정 후 추가한다.

### 8.3 데이터 모델 추가

| 엔티티             | 주요 필드                                                                                                               | 관계 / 제약                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `PushSubscription` | id, userId, endpoint, p256dh, auth, createdAt                                                                           | UNIQUE(endpoint)                   |
| `NotificationLog`  | id, userId, watchId?, channel, templateKey, payload(json), status(`QUEUED`/`SENT`/`FAILED`), error?, sentAt?, dedupeKey | UNIQUE(dedupeKey) — 중복 발송 방지 |

- `User`에 `phone?`, `UserConsent.type`에 `ALIMTALK`, `Watch`에 `channels[]` · `lastNotifiedAt?`을 추가한다.
- 탈퇴 시 푸시 구독도 함께 삭제한다.

### 8.4 작업 큐 · 흐름 추가

| 큐 이름  | 생산자                    | 작업 데이터                                            | 동시성 / 제한                                | 재시도                                              |
| -------- | ------------------------- | ------------------------------------------------------ | -------------------------------------------- | --------------------------------------------------- |
| `notify` | `slots:diff`, 기타 이벤트 | `{ userId, channel, templateKey, payload, dedupeKey }` | 채널별 limiter (알림톡·메일 공급자 TPS 이하) | 5회, 지수 백오프. 4xx(잘못된 수신처)는 재시도 안 함 |

```
slots:diff ─▶ (Watch 가 ACTIVE → AVAILABLE 로 바뀐 경우)
             notify × (Watch × channel)
                 │  dedupeKey = `${watchId}:${slotId}:${channel}`  → NotificationLog UNIQUE로 중복 차단
                 └  발송 성공 → Watch.lastNotifiedAt 기록
```

- **중복 방지**: 같은 감시·슬롯·채널 조합에는 한 번만 보낸다. 재시도·워커 중복 실행에도 `NotificationLog.dedupeKey` UNIQUE 제약이 최종 방어선이 된다.
- 목표 지연: 빈자리 감지 → 알림 발송까지 크롤링 주기 + 30초 이내. 관측 지표에 채널별 발송 성공률을 추가하고, 요청 ID를 알림 발송까지 전파한다.

| 키                                                         | 설명                           |
| ---------------------------------------------------------- | ------------------------------ |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | 웹 푸시                        |
| `MAIL_*`                                                   | 이메일 발송 설정               |
| `ALIMTALK_*`                                               | 알림톡 대행사 키 · 발신 프로필 |

### 8.6 미결 사항 (알림)

1. 카카오 알림톡 발송 대행사 선정, 전화번호 인증 방식, 템플릿 검수 일정.
2. 이메일 발송 수단(SMTP / SES / 외부 서비스)과 발신 도메인(SPF·DKIM 설정).
3. 재알림 정책: 같은 슬롯이 다시 열렸을 때 재알림 여부와 쿨다운 시간.

## 9. 비기능 요구사항

### 9.1 성능

- 조회 API P95 < 300ms(캐시 적중 < 100ms). 테마 목록 `facets`·컬렉션은 Redis 캐시(TTL 5분), 좋아요 변경 시 해당 사용자 관련 캐시만 무효화.
- 빈자리 감지 지연 목표: 슬롯 변화가 크롤링 주기 + 30초 이내에 감시 목록(`/watch/me`)에 반영된다.

### 9.2 신뢰성

- 워커 종료 시 진행 중 작업을 마치고 종료(graceful shutdown, `worker.close()`).
- 소스별 연속 실패 5회면 해당 소스를 자동 일시 중지하고 운영자에게 알린다(`Source.consecutiveFailures`).
- Redis 유실 대비: 반복 작업은 서버 기동 시 DB의 `Source` 기준으로 다시 등록한다(멱등).

### 9.3 관측

- 구조화 로깅(pino). 요청 ID를 API → 큐 작업까지 전파한다.
- 지표: 큐별 대기/실패 수, 소스별 크롤링 성공률·소요 시간.
- 에러 트래킹(Sentry 등). 파서 실패(`CRAWL_PARSE_FAILED`)는 별도 경보를 보낸다.

### 9.4 테스트

- 어댑터: 실제 사이트 HTML/JSON을 **픽스처로 저장**해 파서 단위 테스트를 한다. CI에서는 실제 사이트에 요청하지 않는다.
- API: 테스트용 PostgreSQL·Redis(docker compose)로 e2e 테스트를 돌린다. 응답 엔벨로프·에러 코드가 `shared` 타입과 일치하는지 검증한다.
- 프론트 MSW 목과 실제 API의 응답 형태가 다르면 안 되므로, 목 핸들러도 `shared` 타입을 import하도록 바꾼다.

### 9.5 환경변수 (`backend/.env`)

| 키                                         | 설명                |
| ------------------------------------------ | ------------------- |
| `PORT`                                     | API 포트 (예: 4000) |
| `DATABASE_URL`                             | PostgreSQL 접속 URL |
| `REDIS_URL`                                | Redis 접속 URL      |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | 토큰 서명 키        |
| `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL`       | 토큰 수명           |
| `CORS_ORIGIN`                              | 프론트 오리진       |
| `CRAWLER_USER_AGENT`                       | 크롤러 식별 UA      |
| `CRAWLER_MIN_INTERVAL_MS` | 같은 소스 요청 사이 최소 간격(ms), 기본 3000 |

- 기동 시 zod로 검증하고 누락되면 즉시 종료한다. `.env`는 커밋하지 않고 `.env.example`만 커밋한다.

### 9.6 로컬 개발

```
docker compose up -d          # postgres (redis 는 큐 도입 시 추가)
npm run prisma:migrate -w @escapers/backend   # 최초 1회 · 스키마 변경 시
npm run dev:back              # api (watch)
npm run worker:dev -w @escapers/backend   # worker (watch)
npm run crawl -w @escapers/backend -- all # 테마 데이터 수집 (§7.3)
npm run dev:front             # 실제 백엔드 연결
npm run dev:front:mock        # MSW 목킹 (NEXT_PUBLIC_API_MOCKING=enabled, 백엔드 불필요)
```

## 10. 미결 사항

1. API 프레임워크: NestJS(구조·DI·생태계) vs 순수 Fastify(경량). 본 문서는 NestJS + Fastify 어댑터 기준.
2. ORM: Prisma(DX·마이그레이션) vs Drizzle(SQL 친화·경량). 본 문서는 Prisma 기준.
3. 크롤링 대상 소스 목록과 각 사이트의 약관·`robots.txt` 검토 결과.
4. 예약 내역(`/reservation/me`)의 데이터 출처: 회원 수동 등록 vs 다른 방식. 등록 API 형태 확정 필요.
5. 감시 정책 값: 회원당 감시 개수 상한(10), 크롤링 주기 기본값.
6. 배포 환경: API·워커·Redis·PostgreSQL 호스팅(단일 VM + docker compose vs 매니지드 서비스). Playwright 워커는 메모리 요구량을 고려해야 한다.
7. 요구사항 명세서 §5의 API 경로(`/api/themes` 등 복수형)와 현재 프론트 계약(`/theme`, `/user/getMe` 등) 중 무엇을 기준으로 할지. 본 문서는 **현재 프론트 계약**을 따른다.
8. 알림 관련 미결 사항은 [§8.6](#86-미결-사항-알림) 참고.
9. refreshToken 회전(rotation): §3.3은 재발급 시 회전·재사용 감지를 요구하지만, 현재 프론트 계약(`ReissueResponse`)은 `accessJwt`만 받고 쿠키도 accessToken만 갱신한다. 계약을 바꾸기 전까지 **회전하지 않고**(재발급은 accessJwt만), refreshToken은 해시 저장 · 로그아웃 시 폐기만 한다. 회전을 도입하려면 `ReissueResponse`에 `refreshJwt`를 추가하고 프론트 `reissueAccessToken`이 refreshToken 쿠키도 갱신해야 한다.

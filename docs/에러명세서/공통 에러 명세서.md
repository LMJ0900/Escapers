## 1. 응답 엔벨로프

모든 API 응답은 성공/실패와 무관하게 아래 한 가지 형태를 따른다.

```jsonc
// 성공
{
  "result": "SUCCESS",
  "data": { /* 엔드포인트별 페이로드 */ },
  "error": null
}

// 실패 (HTTP 4xx / 5xx)
{
  "result": "ERROR",
  "data": null,
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS", // 앱 레벨 분기의 키 (안정적 문자열 상수)
    "message": "이메일 또는 비밀번호가 올바르지 않습니다.", // 사용자 노출 가능한 기본 문구
    "status": 401                        // HTTP 상태 (본문에도 중복 포함)
  }
}
```

- `data` 와 `error` 는 상호배타이며 `result` 가 판별자다.
  - `result: "SUCCESS"` → `data` non-null, `error: null`
  - `result: "ERROR"` → `data: null`, `error` non-null

## 2. `result` 필드의 존재 이유

`result` 는 **HTTP 상태 코드와 다른 축**을 표현한다.

| 축                | 질문                                               | 표현 수단        |
| ----------------- | -------------------------------------------------- | ---------------- |
| 통신 계층         | 요청이 서버에 도달했나? 서버가 정상 응답했나?      | HTTP status code |
| 애플리케이션 계층 | 요청한 작업이 실제로 완료됐나? 비즈니스 규칙 만족? | `result` 필드    |

HTTP 는 원래 문서 전송 프로토콜이라 "잔액 부족", "이미 탈퇴한 계정" 같은 도메인 결과를 표현하도록 설계된 게 아니다. `result` 는 그 표현력의 공백을 메운다. 두는 걸로 얻는 것:

1. **응답 형태 단일화** — 호출부는 성공/실패 상관없이 `{ result, data, error }` 하나만 파싱한다.
2. **타입 내로잉** — `result` 를 discriminant 로 `data` / `error` 존재를 타입이 보장한다.
3. **부분 성공(배치) 표현** — 한 요청에 여러 작업이 섞일 때 HTTP status 하나로는 "3건 중 2건 성공"을 못 담는다. 각 항목에 `result` 를 실으면 표현된다.
4. **HTTP 맥락 밖에서의 판별** — 로그 · 큐 · 저장된 JSON 만 봐도 성공/실패를 안다.

> `result` 는 HTTP status 를 **미러링**하는 값이다. 독립적인 판정 근거가 아니라 status 와 항상 일치해야 한다(§4). 프론트의 성공/실패 1차 판정은 트랜스포트 계층에서 HTTP status 로 한다(§5).

## 3. `error` 객체

| 필드      | 타입     | 상태     | 설명                                                                                             |
| --------- | -------- | -------- | ------------------------------------------------------------------------------------------------ |
| `code`    | `string` | **사용** | 앱 레벨 분기의 키. 안정적 문자열 상수.                                                           |
| `message` | `string` | **사용** | 사용자 노출 가능한 기본 문구. **폴백용** — 5xx · 미정의 `code` 에서는 신뢰하지 않는다.           |
| `status`  | `number` | **사용** | HTTP 상태 코드 (본문에 중복 포함). 전송 계층 합성 에러는 `0`.                                    |
| `details` | `object` | **예정** | `code` 별로 형태가 다른 부가 정보 (예: `{ "retryAfter": 300 }`). 도입 전까지 응답에 넣지 않는다. |
| `traceId` | `string` | **예정** | 장애 문의 · 로그 상관용 식별자. 도입 시 5xx 응답에는 필수.                                       |

### 3.1 `code` 사용 규칙

- **앱 레벨 분기는 `code` 로만 한다.** `message` 문자열로 분기하지 않는다(문구는 언제든 바뀐다).
- `code` 가 **없거나 미정의 값**이면 → **HTTP status class 로 폴백**한다.
  - `5xx` → "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요." (재시도 유도)
  - `4xx` → "요청을 처리할 수 없습니다. 입력값을 확인해주세요."
- `code` → 문구 · UI 매핑은 도메인별 매핑 테이블 한 곳에서 관리한다. 흩어진 `if (status === ...)` · `if (message === ...)` 금지.

### 3.2 `message` 사용 규칙

- 프론트는 도메인 매핑 테이블에서 문구를 가져오고, `message` 는 매핑에 없을 때의 폴백으로만 쓴다.
- 백엔드는 5xx 응답의 `message` 에 내부 예외 메시지 · 스택 조각을 넣지 않는다.

---

## 4. HTTP status code 사용 원칙

- **`result` 와 HTTP status 는 항상 일치한다.**
  - `result: "SUCCESS"` → `2xx`
  - `result: "ERROR"` → `4xx` 또는 `5xx`
- **비즈니스 에러도 적절한 4xx 를 쓴다.** (자격증명 불일치 `401`, 권한 없음 `403`, 충돌 `409`, 잠금 `423`, 레이트리밋 `429` 등)
  "전부 `200` 으로 내리고 본문으로만 구분"하는 방식은 쓰지 않는다 — axios 자동 에러 처리 · APM 에러율 집계 · 캐시/프록시가 오작동한다.
- 시스템 에러는 `5xx`.

## 5. 계층별 분기 기준

| 계층        | 분기 기준                                                       | 담당                                             |
| ----------- | --------------------------------------------------------------- | ------------------------------------------------ |
| 트랜스포트  | HTTP status (성공 경로 vs `catch`). 네트워크 에러는 본문이 없음 | `apiClient` / axios interceptor                  |
| 앱 로직     | `error.code` (어떤 문구 · 어떤 UI · 어떤 액션)                  | 컴포넌트 / `useMutation` `onError` / 매핑 테이블 |
| `code` 폴백 | HTTP status class (`4xx` / `5xx`)                               | 매핑 테이블                                      |

`details`(예정)는 분기가 아니라 같은 `code` 의 **렌더 파라미터**다(카운트다운 시간, 소셜 제공자 등).

## 6. 전송 계층(네트워크) 에러

응답 자체가 없는 경우(오프라인 · 타임아웃 · CORS). 서버 본문이 없으므로 **클라이언트가 `error` 를 합성**한다. `status` 는 `0`.

| code               | 판별                                                      | 사용자 메시지                                            |
| ------------------ | --------------------------------------------------------- | -------------------------------------------------------- |
| `NETWORK_OFFLINE`  | `navigator.onLine === false`                              | 인터넷 연결을 확인해주세요.                              |
| `NETWORK_TIMEOUT`  | `AbortController` 타임아웃 (10s)                          | 응답이 지연되고 있습니다. 잠시 후 다시 시도해주세요.     |
| `NETWORK_ERROR`    | 그 외 axios 에러 (CORS · DNS 등)                          | 네트워크 연결에 문제가 있습니다.                         |
| `INVALID_RESPONSE` | 응답은 왔으나 형식 불일치 (JSON 파싱 실패, 엔벨로프 아님) | 일시적인 오류가 발생했습니다.                            |
| `INTERNAL_ERROR`   | 알 수 없는 예외                                           | 일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요. |

> 구현: [`src/api/ApiClient.ts`](../../src/api/ApiClient.ts) `toTransportError`.
> 도메인 문서의 "D. 네트워크/시스템" 절과 코드가 일부 불일치한다(`NETWORK_BLOCKED` vs `NETWORK_ERROR`). **코드 기준 `NETWORK_ERROR` 로 통일**한다.

## 7. 타입 정의 (목표)

```ts
// src/api/ApiRes.ts
export type ApiResponse<TData = null> =
  | { result: "SUCCESS"; data: TData; error: null }
  | { result: "ERROR"; data: null; error: ApiErrorResponse };

// src/api/ApiErrorRes.ts
export interface ApiErrorResponse<TCode extends string = string> {
  code: TCode;
  message: string;
  status: number;
  // details?: Record<string, unknown>;  // 예정
  // traceId?: string;                   // 예정
}
```

### 7.1 코드 반영 (완료)

- [`ApiRes.ts`](../../src/api/ApiRes.ts): `ApiResponse` 를 `result` 기준 discriminated union 으로 변경. 런타임 검사용 `isApiResponse` 추가.
- [`ApiErrorRes.ts`](../../src/api/ApiErrorRes.ts): `data` 슬롯 제거, `status: number` 추가. `isApiErrorResponse` 가드를 `code` + `message` (+ `status` 있으면 `number`) 검사로 변경.
- [`ApiClient.ts`](../../src/api/ApiClient.ts): 엔벨로프 언래핑 — `result === "SUCCESS"` → `data` 반환, `"ERROR"` → `error` 로 reject. 엔벨로프가 아니면 `INVALID_RESPONSE`. 전송 계층 합성 에러는 `status: 0`.
- [`src/mocks/handlers/auth.ts`](../../src/mocks/handlers/auth.ts): 목 응답을 엔벨로프로 감싸도록 수정.

## 8. 폴백 규칙 요약

1. HTTP status 로 성공/실패 판정 (트랜스포트).
2. 실패면 `error.code` 로 분기 (앱).
3. `code` 가 매핑에 없으면 → status class 로 폴백 문구.
4. 응답 형식이 깨졌으면 → `INVALID_RESPONSE`.
5. 응답이 아예 없으면 → 전송 계층 `code` (`NETWORK_*` / `INTERNAL_ERROR`).
